# Design

## Staying asleep

There is one `epoll` loop (`src/loop.c`). Every event source registers file descriptors with it and the process blocks in `epoll_wait`. The only timeout it ever passes is the remaining life of the HUD on screen; with nothing showing it waits forever. Measured on a real, busy Hyprland session: zero context switches over 15 s idle, 2.2 MB PSS and 1.1 MB private memory (the rest of the resident size is shared libraries). With the status icons as Nerd Font glyphs, a freshly started daemon on the same kind of session was 1.4 MB PSS and 0.8 MB private (13.7 MB RSS), and 3.4 MB PSS and 1.2 MB private after its first toasts with glyphs; the same with `icons = theme` was 2.2 MB and 1.2 MB, so the glyphs cost about 1.2 MB of shared, file-backed pages (the font file, mapped once) and next to no private memory. For scale, mako on that machine was 11.1 MB PSS and 7.3 MB private. Start-up is the only busy moment: the audio handshake is four wakeups, and a machine under memory pressure raises its first alert right away. To see what wakes the daemon, build with `make CFLAGS="-O2 -DLOOP_TRACE"`, which logs the fd behind every wakeup to stderr.

The Wayland layer surface and its shared-memory buffer are created when a HUD appears and destroyed when it disappears, so an idle daemon holds no surface and no buffers. The surface is on the overlay layer, takes no keyboard focus and has an empty input region.

The fade uses the `wp_alpha_modifier_v1` protocol: pacreact only changes the surface's opacity multiplier, paced by frame callbacks, and the compositor does the blending, so nothing is redrawn and nothing runs while no HUD is on screen. A new HUD arriving during a fade-out ramps back in from the current opacity. Without that protocol HUDs simply appear and vanish. Some compositors (Hyprland among them) also animate layer surfaces themselves; set `fade_ms = 0` if you prefer only theirs.

## Event sources

Alerts that can fire at start-up (memory, battery) go through `src/alerts.c`, which keeps the last alert shown per source in the state directory so a restart does not repeat it (see [Usage](usage.md#alerts-at-start-up)).

| Source | Mechanism | Idle cost |
|---|---|---|
| Power (`src_power.c`) | Kernel uevents on a `NETLINK_KOBJECT_UEVENT` socket, group 1 (kernel only, no udev). If a battery exists, a 60 s sysfs poll runs only while discharging, because some drivers do not emit uevents on capacity changes. | none |
| Memory (`src_mem.c`) | PSI triggers: write a threshold to `/proc/pressure/memory`, then wait for `EPOLLPRI`. Unprivileged triggers need a window that is a multiple of 2 s. Fallback: a 10 s `MemAvailable` poll. | none (fallback: 1 wakeup / 10 s) |
| Network (`src_net.c`) | rtnetlink link and route events, debounced 1 s, then one route dump to see whether a main-table default route exists. | none |
| Probe (`src_probe.c`) | Opt-in unprivileged ICMP echo (`SOCK_DGRAM`), only while online. | 1 wakeup per interval, only if enabled |
| Backlight (`src_backlight.c`) | `EPOLLPRI` on the sysfs `brightness` attribute, which the kernel signals with `sysfs_notify`. | none |
| Audio (`src_audio.c`) | A small client of the PulseAudio native protocol on the server's unix socket: subscribe to sink, source and server events, then read the default output's and default input's volume, mute state and active port (one request at a time) after a 40 ms debounce. A change of the device's name or of its port is learned without a volume bar, and volume readings for the next 500 ms are learned too: the server moves the port first and applies that port's remembered volume in a second reading. A new default output is a toast, unless a jack event came in the second before (the jack's toast says it). Reconnects with backoff (5 s up to 5 min) if the server is absent or restarts. | none |
| Timers (`timer.c`) | One `CLOCK_REALTIME` `timerfd`, absolute, re-armed to the earliest deadline, with `TFD_TIMER_CANCEL_ON_SET` so clock changes are noticed. | none |
| Printing (`src_print.c`) | CUPS's `org.cups.cupsd.Notifier` signals on the system bus (one more fd in the loop), after a subscription made over IPP on CUPS's unix socket: an HTTP/1.0 POST, built and parsed by hand, renewed halfway through its 24 h lease with one timer. Signals are sent once per subscription, so ours is cancelled on exit, and one left by a pacreact that died is cancelled at the next start-up (they carry `notify-user-data` of `pacreact:PID`, and only those whose process is gone are touched, so a running one keeps its own). `pacreact print` is one Get-Jobs request, made when asked (a 2 s timeout, on a local socket). | none |
| USB (`src_usb.c`) | The same kernel uevent socket as the charger's: an `add` or `remove` of a `usb_device`. The names, `removable` flag and interface classes are read from sysfs after 800 ms, when the interfaces have appeared; a tablet is the HID device whose input node reports a pen button. A remove and an add of the same device within that time cancel out. | none |
| Activity (`activity.c`) | `ext-idle-notify-v1`: the compositor says when the user has been idle for `peek_idle` minutes and when they are back, as events on the Wayland connection that is already in the loop. | none |
| Clock (`clock.c`) | One `CLOCK_REALTIME` `timerfd`, absolute, armed for the next multiple of `clock_every` minutes past the hour and re-armed each time, with `TFD_TIMER_CANCEL_ON_SET`. | 1 wakeup per `clock_every` minutes |
| Use peeks (`timer.c`) | One more `timerfd`, on the monotonic clock, armed for the earliest peek by use and disarmed while the user is away. The monotonic clock does not run in sleep, so sleep is not counted; the boot clock tells how long a sleep was. | none |
| Notifications (`notify.c`) | sd-bus: the bus fd is just another fd in the loop. | none |

Volume is the one source that is not kernel-native: the level lives in the sound server, so pacreact talks to it directly instead of running `pactl`. It works with PulseAudio and with PipeWire's pulse layer (`pipewire-pulse`), which is what was tested. It connects to `$PULSE_SERVER` when that is a `unix:` path or an absolute path, otherwise to `$XDG_RUNTIME_DIR/pulse/native`; TCP servers are not supported. Authentication relies on the server accepting the connecting uid on a local socket, so no cookie is sent.

## How the code is divided

- `hud.c` decides what is on screen and when: the stack, the overflow queue, timeouts, replacement, dismissal, clicks and the on-screen display. It never draws; `paint.c` draws one toast, slider or card at a time (or only measures it) and knows nothing about stacking, so the two are tested apart. A card reaches `paint.c` as a small `CardPaint` view, not as the manager's own item type.
- `display.c` owns the Wayland side. The notification stack and the on-screen display are two `Surface`s (one layer surface with its viewport, fractional-scale object and pending buffer), and share the code that opens, sizes, shows and destroys them. What differs is passed in as two hooks: the stack fades in on its first buffer and tears down its fade state; the on-screen display just attaches and commits.
- `notify.c` reads a `Notify` call in three steps (actions, hints, then the arguments that follow), with the hints in one `Hints` struct, and then acts on it.

## Platform and limits

- Linux with a compositor that implements `wlr-layer-shell`.
- Text: fonts are loaded from known file paths (Noto, DejaVu, Liberation, Noto CJK), not through fontconfig, and the font is chosen per string from its script. Arabic and Hebrew are shaped and reordered with HarfBuzz and FriBidi; Devanagari, Bengali, Gurmukhi, Gujarati, Tamil, Telugu, Kannada, Malayalam, Sinhala and Thai each have their own Noto font, and text that mixes them with Latin is cut into runs, each drawn with its own font (a script font often lacks Latin letters). Other complex scripts (Khmer, Myanmar, Lao, Tibetan, ...) are routed to the DejaVu font, which does not cover them. Runs, and strings, of 160 bytes or more are not shaped. See [Translations](translations.md).
- Scaling follows the compositor through `wp_fractional_scale_v1` and `wp_viewporter`: buffers are rendered at `ceil(size x scale)` pixels and presented at their logical size, so text stays sharp at 1.25x, 1.5x and so on. If the preferred scale changes while a HUD is up (it moved to another monitor), the HUD is drawn again once. Without those protocols it falls back to the nearest whole scale. `scale` pins the scale. Verified: the protocol exchange and the viewport geometry (identical on-screen size at 1x, 1.5x and 2x buffers, in a nested headless compositor, `tests/manual/scale_test.sh`) and the event handling (a unit test). Not verified: a compositor actually running at a fractional scale, because no headless compositor available here could be set to one.
- The output is chosen by the compositor (usually the focused one) unless `output` names one. Checked with two virtual outputs in a nested headless compositor (`tests/manual/output_test.sh`).
- Alarm and timer deadlines are wall-clock time. A large clock step (for example an NTP correction right after boot) shifts them by the same amount.
- Paths exercised only in isolation, not on real hardware, because the development machine is a desktop: battery uevents, charger events, and the backlight notification. (PSI memory triggers were seen firing on real pressure.)
- The notification history is a static ring of 64 fixed-size text entries (no `malloc`, no images, about 60 KB), RAM only by choice: bodies can be private and nothing is written to disk. A replaced card updates its open entry in place, so a progress notification takes one slot. Entries are closed with the spec's `NotificationClosed` reasons, which is why recording happens in `notify.c` where those are emitted; do-not-disturb-skipped ones are recorded as such, and `transient` ones are not recorded. The `persistence` capability is deliberately not advertised: it promises notifications are kept until acknowledged, and a bounded ring that overwrites its oldest does not.
- Security of the history: it is reachable only over the IPC socket (no D-Bus method, file or log output). The socket is bound under `umask(0177)` and the daemon checks `SO_PEERCRED` for the same uid on every client, so permissions going wrong still does not open it; without `$XDG_RUNTIME_DIR` the fallback is a directory `/tmp/pacreact-UID` that is created 0700 and refused unless it is a real directory owned by us and closed to others (a bare socket in `/tmp` could be squatted). `PR_SET_DUMPABLE=0` keeps the ring out of core dumps and out of `/proc/PID/mem` and ptrace for processes of the same user (other users' access is already blocked by the socket). `pacreact history` prints text from arbitrary senders to a terminal, so the listing replaces every C0, DEL and C1 control character, in every field including the app name, with a space. Residual: root, swap, and same-user processes watching the session bus, which no daemon can stop.
- `ActivationToken` (notification spec 1.3) is sent only for a click: xdg-activation-v1 wants the input serial of the event that caused the activation, and a click on a card is the one place pacreact has such a serial (it gets the pointer events itself). The request is asynchronous, so `hud.c` holds the click until the compositor's `done` arrives, ignores further clicks meanwhile and skips a card that left the screen in the meantime; if the protocol or the serial is missing it acts at once with no token. A keybind-driven `pacreact action` has no serial, and compositors do not honour a token without one, so it sends none. pacreact still reports spec version 1.2.
- Icons and sounds are named by the sending app, and a path can be anything. A PNG is therefore opened with `O_NONBLOCK`, must be a regular file of at most 4 MiB, and has its IHDR checked (at most 2048 x 2048) before cairo decodes a byte: without that, a 33-byte file claiming 30000 x 30000 pixels makes cairo allocate gigabytes first, and a FIFO named `x.png` blocks the whole single-threaded daemon. The decode happens once, in `hud_card()`, into the same 64 x 64 raw buffer an `image-data` hint uses, so redraws never touch the disk or the PNG library again (before, every redraw decoded every card's icon twice). Sound paths must be regular files too, or hung players would pile up. Not done: coalescing redraws when notifications arrive in a burst; it needs a dirty flag and a flush in the main loop, and the decode-once change removed the expensive part. A click that waits for an activation token gives up waiting after 2 s, in case a compositor never answers.
- Sound is opt-in everywhere except timers and alarms, on purpose: a desktop that beeps at every plug, link change and message is worse than a silent one. The three event options (`sound_power`, `_DEVICES`, `_NETWORK`) therefore default to nothing, accept `1` for the freedesktop theme's own pair, and play only for changes, never for the state found at start-up (each source already reports that silently). The volume sound (`sound_volume`) is a single sound for the output only (not the microphone, and not an output switch, which is announced by name) and is not held back by do-not-disturb, because it answers an action of the user. The event sounds count as interruptions, so do-not-disturb silences them through `sound_set_quiet()`; alarms and the sounds a notification asks for are decided elsewhere and unaffected. pacreact still passes the player nothing but the file: `pw-play --media-role` and `paplay --property=media.role=event` would let the audio server treat these as event sounds, but they differ between versions and a player that rejects the option would turn the sound into silence, so it is not done.
- Everything in the notification stack is one width (`PAINT_ITEM_W`): toasts used to be as wide as their text and sliders 300 px, which made a stack ragged. A toast now wraps with the same word-wrap as a card body, up to three lines and an ellipsis after that; the on-screen display keeps its narrower slider (`PAINT_OSD_W`), since it is alone on its surface. A fixed width was chosen over "as wide as the widest" because that would make every item change width whenever a long one came and went.
- Long notification bodies: a card shows four lines and opens to 20 on hover (after 250 ms) or with `pacreact expand`. Only cards, because only cards already take the pointer (the input region covers them and nothing else), and because long text comes from apps, not from pacreact's own short toasts. The held state is what makes it usable: a hovered or opened card's timeout waits, and on release it gets at least two more seconds, so reading is never cut off. The pointer's position is kept and re-checked after every redraw (`rehover`), because the layout moves under a still pointer: an opening card pushes the ones below down, a closing one lets them slide back, and a card that expires lets the next slide up. The cost is that moving from an open card to the one below leaves the pointer over empty space once the first closes; one more movement lands on it. Collapsing late would avoid that, at the price of another timer, and was not done. Bodies are stored up to 2048 bytes (they were 512), which is what "the full content" can mean; the history keeps 512.
- The attention deck exists because most notifications do not need the user and are learned to be ignored; a few must not be, so they are drawn somewhere else. The rule is deliberately small and fixed (critical urgency, `category=call.incoming`, and `LEVEL_CRIT` toasts, which is what every system alert at the critical level is) because a place that gets crowded stops meaning anything; it is a flag on the item (`attention`) rather than a configuration language. It is its own layer surface, a third `Surface` beside the stack and the on-screen display, with no fade (attention should not ease in). Items stay in one array in `hud.c`, the stack's first and the deck's after, so expiry, hover, removal and the click tables work over both; only insertion, the caps (4 and 3), refill and rendering know about the two places. The deck is a FIFO whose front never changes by itself: reordering under a pointer is how the wrong card gets clicked, so priority is arrival order, and the only reordering is the user clicking a strip. Strips are narrower, centred and tucked under the card in front instead of offset sideways, because at the top centre a sideways offset would look like a different place and move the click target. Actions, expand and dismiss go to the deck's front card first, since that is what is asking for attention. The deck is turned off (`display_deck_apart`) where it would lie over the stack: with `anchor = top`, and on a screen too narrow for the stack in its top corner and the deck in the middle to clear each other, which is three items, two margins and two gaps, 1204 px. The width is the output's logical width from xdg-output, tracked by a standing listener, not measured when needed: the main loop runs every handler (D-Bus, IPC, timers, which is where notifications arrive) between `display_before_poll` and `display_after_poll`, so asking the compositor synchronously from there, say by opening a probe layer surface and waiting for its configure, would be a nested read on a connection that already has a read pending, and would hang. Which output counts is a guess where it has to be: `output`, else the one a surface last entered, else the narrowest known, because nothing says where the compositor will put the first one. An item's place is decided when it arrives, so one already in the deck stays when the screen changes.
- Size is one factor, not a set of options. Every length and font in `paint.c` is written for a 16 px font and goes through `paint_px()` or `paint_font()`, which multiply by `font_size / 16`; the item width is 380 times the same factor unless `width` fixes it. One knob because a bigger font in a card of the old width wraps badly, so width, padding and icon have to move with it, and because the rest of the layout (the deck's threshold, the click and hover rectangles, the strips) is computed from the measured sizes and follows without being told. The screen-edge margin (16) and the gap the deck needs are not scaled: they are about the screen, not the text. The raw icon buffer stays 64 x 64, so icons are scaled up from it at large sizes. `paint_configure()` is the one place the numbers are set, which is what the tests use. A font file replaces only the Latin slot in `text.c`, since the other scripts need fonts that cover them and the shaping code to match; bold is the same file with `cairo_ft_font_face_set_synthesize()` unless a bold file is named. (Not `cairo_ft_font_face_create_for_ft_face()`'s second argument, which is FreeType's load flags: passing the synthesize constant there is `FT_LOAD_NO_SCALE` and draws the text in font units, many times too large; the text test measures a synthesized bold for that reason.) The file must be a regular file, never opened otherwise, so a pipe cannot block the daemon.
- Status icons are optional all the way down, and are the theme's, not pacreact's. Each message names an icon (with fallbacks, `battery-caution,battery-low`) and `sicon.c` finds it, draws it once at the chosen size and remembers the result, misses included, so a redraw never searches a theme again. A missing icon, no `rsvg-convert` installed, `icons = 0` and a hostile file all come to the same thing: no icon, and the text keeps its room. The lookup prefers the symbolic variant, which has no colour and is drawn as a mask in the text's colour (or the level's), so the icons match the HUD whatever the theme; this is also why a dark-on-light theme icon would not be used as it is. SVG is drawn by running `rsvg-convert` (`-a -w N -h N -f png`) rather than linking librsvg: the library drags in GLib, libxml2, ICU, glycin and libstdc++, which more than doubled the daemon's resident size for a handful of small icons drawn once each. The tool runs out of process, found on `PATH` the first time an SVG is needed, with no shell, only an absolute path as its argument (so a path cannot be taken for an option), stdin and stderr on `/dev/null`, a 1.5 s deadline and a 256 KiB cap on its output, after which it is killed; what it prints is decoded by the same PNG loader as any PNG file, with the same size checks. Symbolic and coloured icons are told apart by name and handled as before; results are cached, so each icon costs one short-lived process (about 10 to 15 ms) per size. The names come from pacreact's code or from the user's own `-i`, never from an app, and have to be theme names, so a notification cannot make pacreact open a file. Which icons appear on which message is in the sources next to the `hud_toast_icon()` calls, since only the source knows what happened. The size is its own setting, not tied to the font unless left alone, because someone who asks for large icons may not want large text and the reverse. Some names have a Nerd Font glyph (`glyph_table` in `sicon.c`: volume, microphone, headphones, headset, webcam, printer), tried first when the first name of the list has one, and drawn as a mask exactly like a symbolic icon, so the painting code knows nothing of it. The font is a file, found by walking the font directories for `SymbolsNerdFont-Regular.ttf` once (or the path in `icon_font`) and opened with FreeType for each drawing and closed after it; a glyph index of 0 means the font lacks it and the theme is used. It is not found by family name through cairo's own font selection, which starts fontconfig: with a few thousand fonts installed that cost about 1.7 MB more private memory and 3 MB more proportional memory in a test program drawing six icons. The font is opened once and kept: opening it for each icon and closing it again does not work, because cairo's scaled-font cache keeps every opened face alive, each with its own pages of the file (six icons held six mappings of a 2.5 MB font, 361 kB each). A build without FreeType (`I18N=0`) has no glyphs. Only the first name is looked at, so `audio-card,audio-headphones` stays the theme's generic card instead of becoming headphones. The unplugged states are names that exist only in the table (`audio-headset-off`, `audio-headphones-off`, `audio-input-microphone-off`, `camera-web-off`, `printer-off`), put in front of the real name: the theme passes over them to the next, so a message does not have to know which source its icon comes from. The code points are Nerd Fonts 3 (`nf-md-*`, U+F0001 and up); they moved from the v2 ones, and were read from the installed font's glyph names, not from memory.
- Sizes with a unit (`margin`, `font_size`, `width`, `icon_size`) use pacommon's `length.[ch]` and are read once as a `Size` (`util.h`), then turned into pixels for the output the HUD is on (`display_px_per_mm()`: the panel's size and mode from `wl_output`, over the scale; 96 dpi if it says nothing sensible) when the HUD starts, and again when the scale changes or the HUD moves to another output. `text_size_min` and `text_size_max` hold the smallest text (`PAINT_SMALLEST_TEXT`) between two lengths by changing the one factor of the previous point, and win over `font_size`; a card is kept inside the screen. `%` is of the output's shorter side, as in the other tools. Pixels stay the default and a bare number is pixels, so no existing file changes.
- Speech is pacommon's `speech.[ch]` with libspeechd (`SPEECH=speechd`, the default; `SPEECH=none` compiles it out). `hud.c` says what an item is when it is put in the stack, not when it arrives, so a notification waiting in the queue is not spoken before it is shown. Speech comes from the daemon, not from the notification's sender, and messages are said one after the other with `speech_say_as(SPEECH_MESSAGE, ...)` (speech-dispatcher keeps the queue, so there is none here and a long burst is said in full, late, and a message never cuts off another); `speech_say()`, which cuts off, is for the tools that want that. `main.c` tells the HUD whether speech opened (`hud_set_speech`), so a bar that moves does not arm a timer when nobody will hear it. Nothing is measured yet for its cost (the binary grows by about 4 KB, and libspeechd is loaded only if `speech` is not `no`).
- The edge margin (`margin`) is the stack's and the deck's distance from the screen, and part of the deck's width rule: more margin needs a wider screen before the deck can sit apart.
- Notification actions are keyboard-driven (`pacreact action N`). The surface's input region covers only the notification cards, so everything else (gaps, toasts, sliders) stays click-through; a click on a card is the spec's `default` action followed by a dismissal. A right click dismisses without invoking anything, which is how a resident card (the `resident` hint: it is not closed after an action is invoked) is removed by mouse. `click = 0` keeps the whole surface click-through. The seat is bound at version 1 and only the pointer is used, so no focus or keyboard state is involved. Checked with a virtual pointer in a nested compositor (`tests/manual/click_test.sh`).
